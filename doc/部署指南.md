## 1. 架构概述

```
                     ┌─────────────────────────────┐
  浏览器 60人  ──────▶│         Nginx               │
                     │  • 静态文件 (Vue 前端)        │
                     │  • 反向代理 /api → 后端       │
                     └────────────┬────────────────┘
                                  │
                     ┌────────────▼────────────────┐
                     │   Uvicorn + FastAPI 后端     │
                     │   监听 127.0.0.1:8000        │
                     │   （单进程，见 2.4）          │
                     └────────────┬────────────────┘
                                  │
                     ┌────────────▼────────────────┐
                     │   SQLite  (app.db, WAL)      │
                     │   config.json / uploads/     │
                     └─────────────────────────────┘
```

**技术栈**
- 后端：Python 3.11 + FastAPI + Uvicorn
- 前端：Vue 3 + Vite（构建为静态文件，由 Nginx 直接服务）
- 数据库：SQLite（文件型，零维护，已开 WAL）
- 反向代理：Nginx

这套架构在 Linux 与 Windows 上**完全一致**，两边的差异只在"怎么装依赖、怎么让进程常驻、
怎么定时备份"这三件事上。

## 2. 环境要求

### 2.1 硬件推荐

| 项目 | 最低配置 | 推荐配置 |
|------|----------|----------|
| CPU  | 2 核     | 4 核     |
| 内存 | 2 GB     | 4 GB     |
| 磁盘 | 20 GB HDD | 50 GB SSD |
| 网络 | 内网百兆 | 内网千兆 |

> 60 人团队的项目管理工具以读操作为主，SQLite 完全胜任。上述配置有充足余量。
> Windows Server 因系统自身开销更大，内存建议直接按 4 GB 起。

### 2.2 操作系统

| 平台 | 推荐版本 | 说明 |
|------|----------|------|
| Linux | **Ubuntu 22.04 LTS** | 长期支持，5 年安全更新。CentOS Stream 9 亦可，包管理命令不同 |
| Windows | **Windows Server 2019 / 2022** | Windows 10/11 专业版也能跑，但缺少服务器级的补丁与远程管理策略 |

### 2.3 软件依赖

| 软件 | 版本 | Linux 获取方式 | Windows 获取方式 |
|------|------|----------------|------------------|
| Python | 3.11+ | `apt install python3.11 python3.11-venv` | [python.org](https://www.python.org/downloads/) 安装包，**勾选 Add to PATH** |
| Node.js | **生产机 18+ 即可**；开发/CI 要 20+（见下） | NodeSource 源 | [nodejs.org](https://nodejs.org/) MSI 安装包 |
| Nginx | 1.18+ | `apt install nginx` | [nginx.org/en/download.html](https://nginx.org/en/download.html) Windows zip，解压到 `C:\nginx` |
| Git | 任意 | `apt install git` | [git-scm.com](https://git-scm.com/) 安装包 |
| SQLite CLI | 3.x | `apt install sqlite3` | [sqlite.org](https://www.sqlite.org/download.html) 的 `sqlite-tools-win` zip，取出 `sqlite3.exe` |
| 服务托管 | systemd（系统自带） | — | **NSSM**（[nssm.cc](https://nssm.cc/download)），Windows 无 systemd |
| 中文字体 | `fonts-noto-cjk`（**必装**） | `apt install fonts-noto-cjk` | 系统自带微软雅黑，**无需处理** |

> **Node 版本分两档，别按最高的那档去要求生产机**：
> - **生产机只做一件事——构建前端**（`npm ci --omit=dev` + `vite build`），Node 18 就够。
> - **开发机与 CI** 还要跑 `npm run lint`（eslint 10）和 `npm run test:e2e`（Playwright），
>   这两个要 **Node 20+**。CI 里用的是 Node 22。
>
> 在 Node 18 的机器上装全套依赖会刷一屏 `npm WARN EBADENGINE`（说 eslint / playwright
> 要 Node 20+）。那些是**警告不是错误**，但也说明装了不该装的东西——生产机按
> [3.5](#35-构建前端两平台相同) 用 `npm ci --omit=dev` 就一条都不会出现。
> Node 18 已经停止维护，新装机器建议直接上 20 或 22；已有的 18 不必为此专门升级。

> **中文字体为什么是 Linux 独有的坑**：专项 Excel 导出里的里程碑时间轴由 PIL 绘制，
> 需要系统有带汉字字形的字体。Windows 自带微软雅黑，Linux 最小化安装通常一个中文字体都没有。
> 代码会自动探测常见字体路径并校验字形，都找不到时**里程碑自动退回表格形式**（不会输出方块乱码），
> 但时间轴图就没有了。字体装在非常规目录可用环境变量 `APP_CJK_FONT=/path/to/font.ttf` 指定。

### 2.4 两条硬性约束（两个平台都适用）

**① 后端只能单进程跑（`--workers 1`）**

APScheduler 定时任务（每日临期扫描、问题单定时采集、每周整页存档）和问题单采集的互斥锁
都是**进程内内存态**。开多个 worker 会让每个 worker 各起一个调度器：
**定时采集重复执行、临期通知一人收到多条、同一份整页存档被反复写**，
采集锁也拦不住并发。60 人的读多写少场景，单 worker 的吞吐绰绰有余（SQLite 已开 WAL，读并发不受影响）。

> 早期版本的本指南写的是 `--workers 2`，与上述单进程假设冲突，现已更正为 1。
> 若你的现网 service 文件里还是 2，升级时顺手改掉。

**② 服务器时区必须是 UTC+8**

数据库里服务端盖章的时间戳存 UTC、出接口时统一转 `+08:00`，这部分与服务器时区无关；
但**报告日期、快照日期、导出文件名**是用服务器本地日期生成的，时区错了会导致
"今天的快照记成昨天"。

```bash
# Linux
sudo timedatectl set-timezone Asia/Shanghai && timedatectl
```
```powershell
# Windows（管理员 PowerShell）
tzutil /s "China Standard Time"; Get-Date
```

## 3. 新环境部署

> **适用**：全新机器、空数据库。做完这一章你会得到一个能登录的系统。  
> **不适用**：已有 `app.db` 的机器——那属于[第 4 章](#4-历史生产升级)。

### 3.0 本章的目录约定

后文命令里的路径按下表替换即可，两个平台结构完全一样：

| | Linux | Windows |
|---|---|---|
| 应用根目录 | `/opt/aipm/app` | `C:\aipm\app` |
| 后端 | `/opt/aipm/app/backend` | `C:\aipm\app\backend` |
| 前端构建产物 | `/opt/aipm/app/frontend/dist` | `C:\aipm\app\frontend\dist` |
| 备份目录 | `/opt/aipm/backups` | `C:\aipm\backups` |
| 日志 | journald（`journalctl`） | `C:\aipm\logs\*.log`（NSSM 重定向） |

### 3.1 安装系统依赖

**Linux**

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y python3.11 python3.11-venv python3-pip
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -   # 18 也能跑，新装直接上 20
sudo apt install -y nodejs
sudo apt install -y nginx git sqlite3 fonts-noto-cjk

python3.11 --version   # Python 3.11.x
node -v                # v20.x.x（18 亦可）
nginx -v               # nginx/1.x.x
```

**Windows**（管理员 PowerShell；也可逐个下载安装包手点）

```powershell
# 若机器能上外网，winget 最省事
winget install --id Python.Python.3.11 -e
winget install --id OpenJS.NodeJS.LTS -e
winget install --id Git.Git -e

# Nginx / NSSM / sqlite3 没有官方 winget 包，手动下载解压：
#   nginx  → C:\nginx
#   nssm   → C:\aipm\tools\nssm.exe
#   sqlite3→ C:\aipm\tools\sqlite3.exe

python --version   # Python 3.11.x
node -v            # v20.x.x（18 亦可）
```

> 内网机器装不了 winget / 连不上外网时，在能上网的机器上下好安装包与 zip 拷进来即可，
> 上述四个组件都不需要联网激活。

### 3.2 拉取代码

**Linux**

```bash
sudo mkdir -p /opt/aipm && sudo chown $USER:$USER /opt/aipm
cd /opt/aipm
git clone <你的仓库地址> app
```

**Windows**

```powershell
New-Item -ItemType Directory -Force C:\aipm | Out-Null
cd C:\aipm
git clone <你的仓库地址> app
```

无论哪个平台，目录结构应是：

```
<应用根目录>/
├── backend/          ← Python 后端
│   ├── main.py
│   ├── requirements.txt
│   ├── config.json   ← **不在版本库里**，从 config.example.json 复制一份，
│   │                    或直接在页面「配置」里保存一次自动生成
│   └── app.db        ← 数据库（首次启动自动创建）
└── frontend/         ← Vue 前端源码
```

### 3.3 安装后端依赖与配置

**Linux**

```bash
cd /opt/aipm/app/backend
python3.11 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

**Windows**

```powershell
cd C:\aipm\app\backend
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

> PowerShell 报「禁止运行脚本」时：`Set-ExecutionPolicy -Scope Process RemoteSigned`。

`config.json` **不跟着代码走**（里面是本机绝对路径与本部署要采集的项目，
属于部署实例的状态，同 `app.db` / `uploads/`）。仓库里给的是模板：

```bash
cd <应用根目录>/backend
cp config.example.json config.json        # Windows: Copy-Item config.example.json config.json
```

不复制也能起来——后端读不到 `config.json` 时回落到模板，页面「配置」里保存一次
就会生成真正的 `config.json`。示例（两平台唯一区别是路径写法）：

```json
{
  "current_stages": ["BFI", "岳麓山", "明场"],
  "issue_report_path": "/opt/aipm/reports",
  "about_content": "岳麓山项目管理系统",
  "hero_badges": ["项目名称", "团队名称", "版本", "阶段"]
}
```

Windows 上 `issue_report_path` 写成 `C:\\aipm\\reports`（JSON 里反斜杠要转义）或
`C:/aipm/reports`（正斜杠同样有效，更省事）。

**必改项：JWT 密钥。** 默认值 `dev-secret-please-change-in-prod` 写在代码里，
生产必须用环境变量覆盖，否则任何拿到源码的人都能伪造登录令牌。

后端认的环境变量一共这几个：

| 变量名 | 必填 | 说明 |
|--------|------|------|
| `APP_SECRET_KEY` | **是** | JWT 签名密钥。随便一串足够长的随机字符即可 |
| `ISSUE_API_COOKIE` | 采集用 | 问题单采集的会话 Cookie，**会过期**，见 [3.9](#39-问题单采集的凭据) |
| `ISSUE_API_APPKEY` | 采集用 | 问题单采集的 AppKey |
| `ISSUE_API_HWID` | 采集用 | 问题单采集的应用 ID（同时用于 `X-HW-ID` 与 `x-app-id`） |
| `ISSUE_API_URL` | 否 | DTS 接口地址，换环境时才需要覆盖 |
| `APP_CJK_FONT` | 否 | 中文字体装在非常规路径时指定（仅 Linux 用得上） |

设置方式见下一节——它属于"服务怎么起"的一部分。

### 3.4 让后端常驻

这是两个平台差异最大的一步。

#### Linux：systemd

```bash
sudo nano /etc/systemd/system/aipm-backend.service
```

```ini
[Unit]
Description=岳麓山项目管理系统后端
After=network.target

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/opt/aipm/app/backend
Environment="PATH=/opt/aipm/app/backend/venv/bin"
Environment="APP_SECRET_KEY=换成你自己的随机串"
ExecStart=/opt/aipm/app/backend/venv/bin/uvicorn main:app \
    --host 127.0.0.1 \
    --port 8000 \
    --workers 1
Restart=always
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable aipm-backend
sudo systemctl start aipm-backend
sudo systemctl status aipm-backend
```

#### Windows：NSSM

Windows 没有 systemd。直接开个 PowerShell 窗口跑 uvicorn 也能用，但**窗口一关服务就停、
重启机器不会自启**，生产必须注册成服务。NSSM 是最省事的方案：

```powershell
$nssm = "C:\aipm\tools\nssm.exe"
& $nssm install aipm-backend "C:\aipm\app\backend\venv\Scripts\uvicorn.exe"
& $nssm set aipm-backend AppParameters "main:app --host 127.0.0.1 --port 8000 --workers 1"
& $nssm set aipm-backend AppDirectory "C:\aipm\app\backend"
& $nssm set aipm-backend AppStdout "C:\aipm\logs\backend.log"
& $nssm set aipm-backend AppStderr  "C:\aipm\logs\backend.err.log"
& $nssm set aipm-backend AppRotateFiles 1
& $nssm set aipm-backend AppEnvironmentExtra "APP_SECRET_KEY=换成你自己的随机串" "PYTHONUTF8=1"
& $nssm set aipm-backend Start SERVICE_AUTO_START
& $nssm start aipm-backend
```

**两个必须设对的参数，设错的表现很隐蔽：**

- **`AppDirectory` 必须是 backend 目录。** 数据库连接串是相对路径 `sqlite:///./app.db`，
  跟随进程工作目录；而 `config.json`、`uploads/` 是按代码文件位置解析的绝对路径。
  工作目录设错时后端**照常启动**，只是会在别处新建一个空库——表现为"页面能开、数据全没了、
  admin/admin123 又能登录了"。查到这一步先别慌，原来的 `app.db` 还在，改对目录重启即可。
- **`PYTHONUTF8=1` 建议加上。** 后端按 UTF-8 读采集脚本的 stdout，而 Windows 中文版的
  Python 默认按 GBK 往管道写文本。**仓库自带的 `fetch_issues_api.py` 已经规避了这点**
  （它用 `sys.stdout.buffer` 直接写 UTF-8 字节），所以不设也能跑；但脚本**报错时**的
  stderr、以及你自己另写的采集脚本都没有这层保护，加上这个变量省事。

不想用 NSSM 也可以用任务计划程序（触发器选"计算机启动时"、"不管用户是否登录都要运行"），
但它没有崩溃自动重启，也不便看日志，不推荐。

### 3.5 构建前端（两平台相同）

```bash
cd <应用根目录>/frontend
npm ci --omit=dev        # 严格按 package-lock.json 装，且跳过只有开发/CI 才用的工具
npm run build            # 产物输出到 frontend/dist/
```

> **为什么是 `npm ci --omit=dev` 而不是 `npm install`**：
> - `npm install` 会在锁文件与 `package.json` 对不上时**顺手改锁文件**，于是各台机器
>   装出各自的依赖版本——生产机上那次构建用了什么，事后谁也说不清。`npm ci` 严格按
>   `package-lock.json` 装，装不上就报错，这正是要的。
> - `--omit=dev` 跳过 `devDependencies`，也就是 **eslint 与 playwright**——那两个只在
>   开发和 CI 里用（代码检查、冒烟测试），生产机一次也用不到，却要求 Node 20+，
>   在 Node 18 的机器上装它们只会刷一屏 `EBADENGINE` 警告。构建真正要的 `vite` 与
>   `@vitejs/plugin-vue` 在 `dependencies` 里，`--omit=dev` 不会漏掉。

> Windows 上如果安装卡在编译原生模块，装一下 Visual Studio Build Tools；
> 本项目依赖为纯 JS，正常情况下不会触发。

### 3.6 配置 Nginx

#### Linux

```bash
sudo nano /etc/nginx/sites-available/aipm
```

```nginx
server {
    listen 80;
    server_name _;          # 替换为实际 IP 或内网域名

    root /opt/aipm/app/frontend/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;   # Vue Router history 模式
    }

    location /api/ {
        proxy_pass         http://127.0.0.1:8000;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_read_timeout 120s;
        client_max_body_size 20M;
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/aipm /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx && sudo systemctl enable nginx
```

#### Windows

Windows 版 Nginx **没有 `sites-available` 那套目录约定**，直接编辑 `C:\nginx\conf\nginx.conf`，
在 `http { }` 里替换掉默认的 `server { }` 块：

```nginx
server {
    listen 80;
    server_name _;

    root   C:/aipm/app/frontend/dist;      # ← 用正斜杠，反斜杠会被当转义符
    index  index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass         http://127.0.0.1:8000;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_read_timeout 120s;
        client_max_body_size 20M;
    }
}
```

Nginx 在 Windows 上是普通控制台程序，同样用 NSSM 注册成服务：

```powershell
& $nssm install aipm-nginx "C:\nginx\nginx.exe"
& $nssm set aipm-nginx AppDirectory "C:\nginx"
& $nssm set aipm-nginx Start SERVICE_AUTO_START
& $nssm start aipm-nginx

# 改完配置后重载（Windows 版没有 systemctl reload）
C:\nginx\nginx.exe -t                # 检查语法
C:\nginx\nginx.exe -s reload         # 重载
```

放行 80 端口（Windows 防火墙默认拦截入站）：

```powershell
New-NetFirewallRule -DisplayName "aipm-http" -Direction Inbound `
    -Protocol TCP -LocalPort 80 -Action Allow
```

### 3.7 验证部署

同网段另一台电脑浏览器访问 `http://<服务器IP>`，看到登录页即成功。

默认管理员账号：**admin / admin123**，**首次登录后立即修改**。

逐项自查：

- [ ] 登录页能打开（Nginx 静态文件 OK）
- [ ] 能登录进首页（后端 + 数据库 OK）
- [ ] 侧边栏 7 个分组都在，随便点几个页面不报 500
- [ ] admin → 用户管理能新建用户（写库 OK）
- [ ] 专项管理 → 新建一个专项 → 导出 Excel，里程碑是**时间轴图片**而不是表格
      （若是表格，说明中文字体没装好，回看 2.3）

### 3.8 新库为什么不用管数据库迁移

后端启动时按固定顺序做四件事：`ensure_schema()`（老库补列）→ `create_all()`（建缺失的表）→
Alembic 追平 → 写入种子数据。

对**空库**来说，`create_all()` 已按当前模型把所有表连所有列一次建齐，后续 Alembic 迁移
逐个检查后发现无事可做，全部空转跳过。所以新环境部署**不需要执行任何 alembic 命令**，
也不存在"漏跑迁移"的风险——这正是它和第 4 章最本质的区别。

### 3.9 问题单采集的凭据

问题单的每日自动采集由后端以子进程方式调用
[backend/scripts/fetch_issues_api.py](../backend/scripts/fetch_issues_api.py)，
脚本带着三个认证头去调 DTS 接口。这些凭据**不要写进脚本**，用环境变量配：

| 变量名 | 对应请求头 | 说明 |
|--------|-----------|------|
| `ISSUE_API_COOKIE` | `Cookie` | 会话 Cookie，**会过期**，是日常唯一需要定期更换的 |
| `ISSUE_API_APPKEY` | `X-HW-APPKEY` | 应用密钥 |
| `ISSUE_API_HWID` | `X-HW-ID` + `x-app-id` | 应用 ID，两个头共用这一个值 |
| `ISSUE_API_URL` | — | 接口地址，默认已指向生产 DTS，换环境才需要覆盖 |

**为什么不直接改脚本里的默认值：**

- 凭据一旦提交就**永久留在 git 历史里**，事后删掉也追不回来；
- Cookie 会过期，写在代码里意味着每次换凭据都要改代码、提交、重新部署；
- 同一份代码要在测试机和生产机跑不同账号时，改代码的做法没法共存。

> 脚本顶部目前**仍保留了一份明文默认值作回退**（历史遗留），所以不配环境变量也能跑。
> 但这正是上面三条问题的来源——生产上请把环境变量配好，之后可以把脚本里的默认值清空。

#### 怎么设

**Linux**：写进 systemd service 的 `[Service]` 段，与 `APP_SECRET_KEY` 并列：

```ini
Environment="APP_SECRET_KEY=换成你自己的随机串"
Environment="ISSUE_API_COOKIE=prod_J_SESSION_ID=xxxxxxxx"
Environment="ISSUE_API_APPKEY=xxxxxxxx"
Environment="ISSUE_API_HWID=xxxxxxxx"
```

```bash
sudo systemctl daemon-reload && sudo systemctl restart aipm-backend
```

**Windows**：追加到 NSSM 的 `AppEnvironmentExtra`（**一次要把所有变量都列全**，
这个命令是整体覆盖，不是追加）：

```powershell
& $nssm set aipm-backend AppEnvironmentExtra `
    "APP_SECRET_KEY=换成你自己的随机串" `
    "PYTHONUTF8=1" `
    "ISSUE_API_COOKIE=prod_J_SESSION_ID=xxxxxxxx" `
    "ISSUE_API_APPKEY=xxxxxxxx" `
    "ISSUE_API_HWID=xxxxxxxx"
& $nssm restart aipm-backend
```

> ⚠️ **必须重启后端才生效。** 采集脚本是后端起的子进程，继承的是**后端进程启动那一刻**的
> 环境变量。只改 service 配置不重启，采集还是用旧凭据——表现为"明明换了 Cookie 还是 401"。
> 别在自己的登录会话里 `export` / `$env:` 设一遍就以为好了，那只对你当前这个终端有效。

#### 验证

脚本自带排障模式，直接打印 HTTP 状态、总数、首条记录字段名：

```bash
cd <应用根目录>/backend
source venv/bin/activate                   # Windows: .\venv\Scripts\Activate.ps1
python scripts/fetch_issues_api.py YLS3000 --peek
```

- `http_status: 200` 且 `total` 有数 → 凭据可用；
- 401 / 提示未登录 → Cookie 过期，换新的；
- `You do not have the permission…` → 凭据没问题，是这个账号对该产品没有查询权限，
  换一个有权限的项目试，或找 DTS 侧开权限。

命令行验证通过后，再去页面点一次「立即采集」确认后端进程也拿到了新凭据——
**这两步验的不是同一件事**：命令行用的是你终端的环境变量，页面用的是后端服务的。

#### Cookie 过期了怎么换

日常运维里唯一的重复动作。表现是采集突然全线失败，「采集日志」页签里是 401 或未登录：

1. 在浏览器里重新登录 DTS，从开发者工具的请求头里复制 `prod_J_SESSION_ID=...`；
2. 按上面「怎么设」改 `ISSUE_API_COOKIE`；
3. **重启后端**；
4. `--peek` 验一次，再到页面点「立即采集」。

**不需要**改代码、不需要重新构建前端、不需要跑迁移。

#### 新增项目 tab 时别忘了 pbiName

页面上的项目 tab 由 `config.issue_api_projects` 决定，而每个项目查哪条产品基线由脚本里的
`PROJECT_PARAMS` 决定，**两边要对齐**：

```python
PROJECT_PARAMS = {
    "YLS3000": {"pbiName": "YLS3000 V100R001C00"},
    "YLS5000": {"pbiName": "YLS5000 V100R001C10"},
    "YLS8000": {"pbiName": "YLS8000 V200R001C00"},
}
```

只加了 tab 没加 `PROJECT_PARAMS` 时，脚本会按 `<项目名> V100R001C00` 兜底去查，
多半查不到，报「DTS 接口未返回数据」。

## 4. 历史生产升级

> **适用**：机器上已经在跑、`app.db` 里有真实数据，要升到新版本。  
> **不适用**：全新机器——那是[第 3 章](#3-新环境部署)。

### 4.1 升级前必做

**① 备份。** 没有例外，哪怕是"只改了前端"的版本：

```bash
/opt/aipm/backup.sh                      # Linux
```
```powershell
powershell -File C:\aipm\backup.ps1      # Windows
```

备份脚本的写法见 [6. 数据备份与恢复](#6-数据备份与恢复)。还没建过备份脚本的，
**先去建**，再回来升级。

**② 记下当前版本**，回滚时要用：

```bash
cd <应用根目录> && git log --oneline -1
```

**③ 确认当前数据库的迁移版本**（决定要不要做 [4.5](#45-一次性检查你的库是不是卡在-0002) 的一次性检查）：

```bash
cd <应用根目录>/backend
source venv/bin/activate          # Windows: .\venv\Scripts\Activate.ps1
alembic current
```

> `alembic current` 必须在 **backend 目录**下执行——数据库路径是相对的，
> 在别的目录跑会连到一个不存在的空库，输出一片空白，看着像"没接入 Alembic"。

**④ 查一遍你要跨过的版本有没有额外步骤。**

常规升级步骤（4.2 / 4.3）是不变的，但**个别版本动了已有数据**，需要一次性的额外操作。
在 [升级历史](升级历史.md) 的索引表里，从你现在的版本往上数到要升到的版本，
中间跨过的每一条都要看一眼——升级是累积的，跳过中间版本不代表跳过它的数据变更。

> 这一步经常被跳过，因为漏掉的后果**不长得像故障**：页面照常打开、功能照常点，
> 只是某一列数据从此不再更新，或者某个采集悄悄停了。


### 4.2 标准升级步骤（Linux）

```bash
cd /opt/aipm/app

# 1. 拉取最新代码
git pull origin main

# 2. 更新后端依赖（requirements.txt 有变化时才实际安装）
cd backend
source venv/bin/activate
pip install -r requirements.txt

# 3. 重启后端
#    create_all 自动建新表，automigrate 自动把 Alembic 追平到 head
sudo systemctl restart aipm-backend
sudo systemctl status aipm-backend

# 4. 确认迁移真的追平了（关键，别跳过）
alembic current                  # 应显示最新 revision 且带 (head)

# 5. 重新构建前端
cd ../frontend
npm ci --omit=dev
npm run build

# 6. 刷新 Nginx（静态文件已换，reload 即可）
sudo systemctl reload nginx
```

后端停服时间不超过 10 秒；前端产物覆盖 `dist/` 后用户刷新浏览器即见新版本。

> **跑之前先翻一下 [升级历史](升级历史.md)**：部分版本在标准流程之外还有必做步骤
> （数据回填要人工确认、口径变更要核对、回滚方式不同）。当前最新一条要动手三步，
> **其中「体检版本三层」那步一定要跑**。

### 4.3 标准升级步骤（Windows）

```powershell
cd C:\aipm\app

# 1. 拉取最新代码
git pull origin main

# 2. 更新后端依赖
cd backend
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt

# 3. 重启后端服务
Restart-Service aipm-backend
Get-Service aipm-backend

# 4. 确认迁移真的追平了（务必在 backend 目录下执行）
alembic current

# 5. 重新构建前端
cd ..\frontend
npm ci --omit=dev
npm run build

# 6. 重载 Nginx
C:\nginx\nginx.exe -t
C:\nginx\nginx.exe -s reload
```

**Windows 专有的两个坑：**

- **文件占用导致 `git pull` 失败。** 后端服务持有 `.pyc`、日志等文件句柄，
  偶尔会让 pull 或 `npm run build` 报"另一个程序正在使用此文件"。
  先 `Stop-Service aipm-backend`，拉完代码装完依赖再 `Start-Service`。
- **`Restart-Service` 秒回不代表起来了。** NSSM 重启是异步的，紧接着跑 `alembic current`
  可能撞上启动中的写锁。稳妥做法是重启后先 `Get-Service` 确认 Running，再往下走。

> 同样：**升级前先翻 [4.6](#46-特定版本升级说明)**，看这一版有没有标准流程之外的必做步骤。

### 4.4 数据库结构是怎么追平的

**v0.26.0 起用 Alembic 管理结构变更**，三条通道并存，各管一段：

| 机制 | 负责 | 何时运行 |
|------|------|----------|
| `create_all`（`main.py` 启动时） | **新建整张表** | 重启后端自动 |
| Alembic（`backend/alembic/`） | **给已有表加列 / 改名 / 删列 / 改类型 / 加约束 / 数据回填** | 重启后端自动（`automigrate.py`） |
| `migrate.py`（**已冻结**） | 历史遗留的 `ADD COLUMN`，不再新增 | 重启后端自动 |

✅ **迁移是自动的**：后端启动时 `automigrate.py` 把 Alembic 追平到 head：

- 库还没被 Alembic 跟踪（无 `alembic_version` 表）→ 自动 `stamp 0001_baseline` 再 upgrade，
  从 v0.26 以前升级也**无需手动 stamp**；
- 已跟踪 → 直接 upgrade（无新迁移时是毫秒级空操作）。

⚠️ **但失败是静默的**：迁移异常只记一行 warning、**不阻塞启动**（延续"迁移不该拖垮服务"的原则）。
后果是**整条升级链停在出错那一版，后面的迁移全部不执行**，而服务看起来一切正常。
所以 [4.2](#42-标准升级步骤linux) / [4.3](#43-标准升级步骤windows) 的第 4 步
（`alembic current` 确认到 head）不是可选项。

版本没追平时，先看日志里的 `automigrate` 告警：

```bash
sudo journalctl -u aipm-backend -n 100 --no-pager | grep -i automigrate   # Linux
```
```powershell
Select-String -Path C:\aipm\logs\backend*.log -Pattern automigrate | Select-Object -Last 20
```

再手工执行一次看完整报错：

```bash
cd <应用根目录>/backend && alembic upgrade head
```

> 若报唯一约束 / 外键冲突，多半是存量脏数据，按报错清理后重试。
> 升级前已用 `PRAGMA foreign_key_check` 核验过生产库无悬空外键，启用外键强制是安全的。

### 4.5 一次性检查：你的库是不是卡在 0002

**这是一个已修复的历史缺陷，但已经跑过 v0.27~v0.29 的生产库需要确认一次。**

`0003_special_section_order` 曾经缺少幂等守卫：它要加的列 `migrate.py` 里也有一份，
而 `ensure_schema()` 跑在 Alembic 之前——轮到 Alembic 时列已存在，`ALTER TABLE` 抛
`duplicate column name`，被 `automigrate` 吞成一行 warning。表现不是启动失败，而是
**升级链卡死在 `0002`，`0004`~`0007` 从未执行过**。

**症状（有真实数据影响，不只是版本号难看）：**

| 没跑到的迁移 | 你会看到什么 |
|---|---|
| `0004` | 升级到 v0.28 后，客户面状态里**历史的关键事务 / 软件类问题条目全空**（数据没丢，只是没搬进新表） |
| `0005` | 问题跟踪的责任领域 / 问题进展 / 分类列缺失，相关页面 500 |
| `0007` | 硬件清零的自定义列存不住（`extra_fields_json` 缺列） |
| `0008` | 专项详情页 500：`no such column: section_config_json` |

**检查与修复：**

```bash
cd <应用根目录>/backend
source venv/bin/activate                 # Windows: .\venv\Scripts\Activate.ps1
alembic current
```

- 显示 `0002_unify_product_priority` → **中招了**，拉取含修复的代码后重启后端即可，
  一次启动会把 `0003 → 0008` 全部补跑完（含 `0004` 的数据回填）。所有迁移都是幂等的，
  重复执行安全。
- 显示最新 revision 带 `(head)` → 正常，跳过本节。
- 什么都没输出 → 大概率是没在 backend 目录下执行（见 [4.1](#41-升级前必做) 的提示）；
  确认目录没错还是空的，说明这库还没接入 Alembic，重启后端会自动 stamp 并追平。

修复后再确认一次数据：打开「客户面状态」总览，历史的关键事务 / 问题条目应当回来了。

### 4.7 回滚

升级后发现严重问题时，按"代码 → 数据"的顺序回退，**大多数版本只需回退代码**：

**Linux**

```bash
cd /opt/aipm/app
git log --oneline -10          # 找到升级前的 commit
git checkout <commit-hash>

sudo systemctl restart aipm-backend
cd frontend && npm ci --omit=dev && npm run build
sudo systemctl reload nginx
```

**Windows**

```powershell
cd C:\aipm\app
git log --oneline -10
git checkout <commit-hash>

Restart-Service aipm-backend
cd frontend; npm ci --omit=dev; npm run build
C:\nginx\nginx.exe -s reload
```

**要不要一起回退数据库？** 看该版本在 [4.6](#46-特定版本升级说明) 里的「回滚」小节：

- 绝大多数版本**不需要**——新表和新列对旧代码是隐形的（SQLAlchemy 只 SELECT 已映射列）。
- 涉及数据回填 / 格式转换的版本（如 `0002` 优先级映射、`0004` 客户面问题搬迁）才需要还原
  `app.db`，做法见 [6.4](#64-从备份恢复)。
- 还原 `app.db` 会**丢掉升级后录入的所有数据**，动手前先确认这是你想要的。

## 5. Linux 与 Windows 差异速查

架构、代码、数据库文件格式在两个平台上完全一样，`app.db` 可以直接互拷。差异只有这些：

| 事项 | Linux | Windows |
|------|-------|---------|
| 应用根目录 | `/opt/aipm/app` | `C:\aipm\app` |
| 虚拟环境激活 | `source venv/bin/activate` | `.\venv\Scripts\Activate.ps1` |
| 服务托管 | systemd | NSSM（无 systemd） |
| 启动后端 | `sudo systemctl start aipm-backend` | `Start-Service aipm-backend` |
| 重启后端 | `sudo systemctl restart aipm-backend` | `Restart-Service aipm-backend` |
| 看后端日志 | `journalctl -u aipm-backend -f` | `Get-Content C:\aipm\logs\backend.log -Wait` |
| 设环境变量 | service 文件的 `Environment=` | `nssm set <svc> AppEnvironmentExtra` |
| 工作目录 | service 文件的 `WorkingDirectory=` | `nssm set <svc> AppDirectory`（**必设**） |
| Nginx 配置 | `/etc/nginx/sites-available/aipm` | `C:\nginx\conf\nginx.conf`（无 sites-* 目录） |
| Nginx 路径写法 | `/opt/aipm/...` | `C:/aipm/...`（**用正斜杠**） |
| Nginx 重载 | `sudo systemctl reload nginx` | `C:\nginx\nginx.exe -s reload` |
| 定时任务 | cron | 任务计划程序 / `schtasks` |
| 备份脚本 | bash + `sqlite3` | PowerShell + `sqlite3.exe` |
| 中文字体 | **需装** `fonts-noto-cjk` | 系统自带，无需处理 |
| 子进程编码 | 默认 UTF-8，无需处理 | 建议设 `PYTHONUTF8=1`（自带采集脚本已自行规避，自写脚本需要） |
| 防火墙 | 内网通常无需处理 | `New-NetFirewallRule` 放行 80 |
| 时区设置 | `timedatectl set-timezone Asia/Shanghai` | `tzutil /s "China Standard Time"` |

**Windows 独有的注意点小结**（都在前文展开过，这里汇总一次）：

1. `AppDirectory` 设错 → 后端在别处新建空库，表现为"数据全没了"；
2. 缺 `PYTHONUTF8=1` → 自写的采集脚本打印中文时按 GBK 编码，后端按 UTF-8 读会乱码
   （仓库自带的脚本已规避）；
3. 服务持有文件句柄 → `git pull` / `npm run build` 偶发"文件被占用"，先停服务；
4. Nginx 配置里的反斜杠会被当成转义符，一律写正斜杠。

## 6. 数据备份与恢复

### 6.1 需要备份什么

| 文件 | 位置 | 重要性 |
|------|------|--------|
| `app.db` | `backend/app.db` | ★★★ 所有业务数据 |
| `uploads/` | `backend/uploads/` | ★★★ 用户上传的附件、全景图、license 文件 |
| `config.json` | `backend/config.json` | ★★☆ 配置参数 |
| 报表文件 | `issue_report_path` 指定目录 | ★★☆ 原始数据 |
| 问题单快照明细 | `issue_snapshot_dir`（默认 `backend/data/issue_snapshots/`） | ★★☆ 趋势数字在库里，明细钻取靠这些 JSON |
| 采集 Excel 备份 | `issue_excel_raw_dir` / `issue_excel_analysis_dir`（默认 `backend/data/issue_excel/`） | ★☆☆ 可再生成 |

> `app.db` 开了 WAL，同目录下还会有 `app.db-wal` / `app.db-shm`。**不要直接拷这三个文件**，
> 用下面的 `.backup` 命令——它会把 WAL 里未合并的事务一起落进备份文件。

> **库会随「整页存档」稳定长大**：每周一 07:00 给每个专项 / 领域 / 客户面 /
> 硬件清零各存一份当时的整页数据（见 [升级历史](升级历史.md) 第 21 条），
> 一份从几 KB 到几十 KB 不等。按几十个对象估，一年增量在几十到几百 MB 这个量级，
> 对 SQLite 不构成问题，但**备份文件会跟着变大**，按大小做保留策略的脚本要留意。
> 确实要清理时在「知识管理 → 历史存档」里逐份删（仅 admin），
> 不要直接去库里 `DELETE`——存档就是给人回溯用的，删掉了补不回来。

### 6.2 在线备份（不需要停服）

**Linux**

```bash
sqlite3 /opt/aipm/app/backend/app.db ".backup /opt/aipm/backups/app-$(date +%Y%m%d-%H%M%S).db"
```

**Windows**

```powershell
$ts = Get-Date -Format 'yyyyMMdd-HHmmss'
& C:\aipm\tools\sqlite3.exe C:\aipm\app\backend\app.db ".backup 'C:/aipm/backups/app-$ts.db'"
```

### 6.3 自动定时备份（推荐）

#### Linux：脚本 + cron

```bash
sudo mkdir -p /opt/aipm/backups && sudo chown $USER:$USER /opt/aipm/backups
nano /opt/aipm/backup.sh
```

```bash
#!/bin/bash
set -e

BACKUP_DIR="/opt/aipm/backups"
APP_DIR="/opt/aipm/app/backend"
DATE=$(date +%Y%m%d-%H%M%S)

sqlite3 "$APP_DIR/app.db" ".backup ${BACKUP_DIR}/app-${DATE}.db"   # 在线热备份
cp "$APP_DIR/config.json" "${BACKUP_DIR}/config-${DATE}.json"
tar -czf "${BACKUP_DIR}/uploads-${DATE}.tar.gz" -C "$APP_DIR" uploads

# 保留最近 30 天
find "$BACKUP_DIR" -name "app-*.db"          -mtime +30 -delete
find "$BACKUP_DIR" -name "config-*.json"     -mtime +30 -delete
find "$BACKUP_DIR" -name "uploads-*.tar.gz"  -mtime +30 -delete

echo "[$(date)] 备份完成：app-${DATE}.db"
```

```bash
chmod +x /opt/aipm/backup.sh
/opt/aipm/backup.sh          # 先手动测一次
crontab -e
```

```
0 2 * * * /opt/aipm/backup.sh >> /var/log/aipm-backup.log 2>&1
```

#### Windows：PowerShell 脚本 + 任务计划

`C:\aipm\backup.ps1`：

```powershell
$ErrorActionPreference = 'Stop'

$BackupDir = 'C:\aipm\backups'
$AppDir    = 'C:\aipm\app\backend'
$Sqlite    = 'C:\aipm\tools\sqlite3.exe'
$ts        = Get-Date -Format 'yyyyMMdd-HHmmss'

New-Item -ItemType Directory -Force $BackupDir | Out-Null

# 在线热备份（注意目标路径用正斜杠 + 单引号）
& $Sqlite "$AppDir\app.db" ".backup '$($BackupDir -replace '\\','/')/app-$ts.db'"
Copy-Item "$AppDir\config.json" "$BackupDir\config-$ts.json"
Compress-Archive -Path "$AppDir\uploads\*" -DestinationPath "$BackupDir\uploads-$ts.zip" -Force

# 保留最近 30 天
Get-ChildItem $BackupDir -Include 'app-*.db','config-*.json','uploads-*.zip' -Recurse |
    Where-Object { $_.LastWriteTime -lt (Get-Date).AddDays(-30) } |
    Remove-Item -Force

Write-Output "[$(Get-Date)] 备份完成：app-$ts.db"
```

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File C:\aipm\backup.ps1   # 先手动测一次

schtasks /create /tn "aipm-backup" /sc daily /st 02:00 /ru SYSTEM `
  /tr "powershell -NoProfile -ExecutionPolicy Bypass -File C:\aipm\backup.ps1"
```

### 6.4 从备份恢复

思路两边一样：**停服 → 换文件 → 起服**。旧库先留一份，别直接覆盖掉。

**Linux**

```bash
sudo systemctl stop aipm-backend

cp /opt/aipm/app/backend/app.db /opt/aipm/app.db.broken
cp /opt/aipm/backups/app-20260817-020001.db /opt/aipm/app/backend/app.db
rm -f /opt/aipm/app/backend/app.db-wal /opt/aipm/app/backend/app.db-shm

sudo systemctl start aipm-backend
```

**Windows**

```powershell
Stop-Service aipm-backend

Copy-Item C:\aipm\app\backend\app.db C:\aipm\app.db.broken
Copy-Item C:\aipm\backups\app-20260817-020001.db C:\aipm\app\backend\app.db -Force
Remove-Item C:\aipm\app\backend\app.db-wal,C:\aipm\app\backend\app.db-shm -ErrorAction SilentlyContinue

Start-Service aipm-backend
```

> 换库后**必须删掉残留的 `-wal` / `-shm`**：它们属于旧库，留着会让 SQLite 把旧事务
> 往新库上合并，轻则数据错乱重则报库损坏。

恢复的库如果比当前代码旧，启动时 `automigrate` 会自动把它追平到 head，无需手工干预；
但仍建议照 [4.4](#44-数据库结构是怎么追平的) 跑一次 `alembic current` 确认。

## 7. 常见问题排查

### 7.1 后端无法启动

**Linux**

```bash
sudo journalctl -u aipm-backend -n 50 --no-pager
```

**Windows**

```powershell
Get-Content C:\aipm\logs\backend.err.log -Tail 50
Get-Service aipm-backend
```

常见原因（两平台通用）：

- Python 版本不符：确认虚拟环境里的 `python --version` 为 3.11+
- 端口占用：Linux `sudo ss -tlnp | grep 8000`；Windows `netstat -ano | findstr :8000`
- `config.json` 格式错误：`python -m json.tool config.json` 验证

Windows 补充：服务能装上但一起就停，多半是 `AppDirectory` / `AppParameters` 写错，
用 `nssm edit aipm-backend` 打开图形界面核对。

### 7.2 页面能打开，但数据像是"全没了"

**先别重装。** 优先怀疑后端连到了错误的数据库文件——`app.db` 是相对工作目录解析的：

- Linux：service 文件的 `WorkingDirectory` 是否指向 backend 目录；
- Windows：`nssm get aipm-backend AppDirectory` 是否指向 backend 目录。

设错时后端会在工作目录下新建一个空库，seed 出 admin/admin123，看起来"能用但数据没了"。
原来的 `app.db` 还在原地，改对目录重启即恢复。找一下哪个是真库：

```bash
find / -name "app.db" -size +100k 2>/dev/null          # Linux
```
```powershell
Get-ChildItem C:\ -Recurse -Filter app.db -ErrorAction SilentlyContinue |
  Where-Object Length -gt 100kb | Select-Object FullName,Length,LastWriteTime
```

### 7.3 版本管理页「只剩第一层」——大版本还在，版本和迭代版本都没了

**数据没丢，是没挂上。** 版本页是「大版本 → 版本 → 迭代版本」三层嵌套渲染的，
`release_version_id` 为空的迭代行**在页面上完全不可见**，看着就像整层数据蒸发了。

成因：SQLite 下 Alembic 是 non-transactional DDL，`0010` 若中途失败，加过的列会留在库里；
下次启动重跑时，它的回填守卫看到 `release_versions` 已经非空就整段跳过，
剩下的迭代行再也挂不上版本。

**先确认，再动手**（脚本默认只读）：

```bash
cd <应用根目录>/backend
source venv/bin/activate                 # Windows: .\venv\Scripts\Activate.ps1
python scripts/repair_version_tiers.py
```

看「迭代版本 N，其中**没挂上版本**的 M 条」：

- **M > 0** → 就是这个问题。重启一次后端即可，`0012` 会自动挂回去（只挂接不删除，可反复跑）；
  想顺手清掉「本身就是一个版本、且无人引用」的冗余行，就 `cp app.db app.db.bak` 后
  加 `--apply` 跑脚本。
- **M = 0 且版本数也是 0** → 库里本来就没有这层数据，不是挂丢了。
- **M = 0 且版本数不为 0** → 数据是好的，问题在页面：确认选对了项目 Tab，
  并展开大版本行左侧的箭头（大版本行上的「下辖 N 版本 / M 构建」计数可以直接印证）。

详见 [升级历史](升级历史.md) 里「补记」那一条的验证步骤。

### 7.4 升级后某个页面 500

八成是迁移没追平，按 [4.4](#44-数据库结构是怎么追平的) 与 [4.5](#45-一次性检查你的库是不是卡在-0002) 查：

```bash
cd <应用根目录>/backend && alembic current        # 是否到 head
```

日志里 `no such column: xxx` 基本可以直接确诊。

### 7.5 前端页面空白 / 404

```bash
sudo nginx -t                          # Linux：检查配置语法
ls /opt/aipm/app/frontend/dist/        # 确认构建产物存在
sudo tail -f /var/log/nginx/error.log
```
```powershell
C:\nginx\nginx.exe -t                  # Windows

```

Windows 上还有一个高频原因：`root` 写成了反斜杠路径。改成 `C:/aipm/app/frontend/dist`。

### 7.6 API 请求 502 Bad Gateway

后端没运行或崩了：

```bash
sudo systemctl status aipm-backend && sudo systemctl restart aipm-backend   # Linux
```
```powershell
Get-Service aipm-backend; Restart-Service aipm-backend                      # Windows
```

### 7.7 问题单采集失败

- 报 401 / 未登录 / 无数据 → **Cookie 过期**，按 [3.9](#39-问题单采集的凭据) 换
  `ISSUE_API_COOKIE` 并**重启后端**；换完先用 `--peek` 验一次。
- 报「You do not have the permission…」→ 凭据有效，是账号对该产品没查询权限。
- 报「DTS 接口未返回数据」→ 先看该项目在脚本 `PROJECT_PARAMS` 里的 `pbiName` 对不对
  （新加的项目 tab 常漏配，见 3.9 末尾）。
- 报「输出不是合法 JSON」且日志里有乱码 → 编码问题，给服务加 `PYTHONUTF8=1`（见 3.4）。
- 报「脚本执行超时」→ 在「问题单管理 → 配置 → 定时采集」里调大脚本超时秒数。

### 7.8 「解决」的数字里混着还在处理的单

「新增/解决」是**相邻两次快照的编号差集**——`解决 = 上次有、今天没有`，
**从不读问题单的状态**。所以任何让一行掉出快照的原因都会记成一笔「解决」。
点开那天「解决」的抽屉，看列表里的「进展」和「当前责任人」，对号入座：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 进展里带「关闭」字样但明显没闭环（待关闭 / 申请关闭…） | 状态剔除是**子串**匹配 | 在「配置 → ...」调整 `issue_exclude_statuses`，或接受这个粗口径 |
| 责任人换成了陌生名字 | 转给了统计部门以外的人 | 部门过滤是有意为之；确认这单确实不归本部门管 |
| 责任人换了人、但部门没问题 | 早期版本会把不在小组名单里的人整行丢掉 | 已修复。到「配置 → 小组配置 → 未归组责任人」补名单 |
| 条数接近 200 或它的倍数、下一天又「新增」回来 | 采集**只拉回了一部分**（DTS 会话中途失效返回 200 + 空页） | 已修复：现在这种情况直接让采集失败、不落快照。老快照重新采集覆盖那一天；先按 [7.7](#77-问题单采集失败) 换 Cookie |

最硬的判据是**同一个编号后来又出现在「新增」里**——它从来没被解决过，
只是中途掉出去又回来了。


- 定时没跑但手动能跑 → 看「配置 → 定时采集 → 当前状态」，确认开关是启用的、执行时刻没过。
- 详细失败原因看各项目 tab 的「采集日志」页签（含脚本 stderr 尾部）。

### 7.9 `npm` 装依赖时刷一屏 `EBADENGINE`

```
npm WARN EBADENGINE Unsupported engine {
npm WARN EBADENGINE   package: 'playwright-core@1.62.1',
npm WARN EBADENGINE   required: { node: '>=20' },
npm WARN EBADENGINE   current: { node: 'v18.16.0', npm: '9.5.1' }
npm WARN EBADENGINE }
```

**这些是警告不是错误**，构建照样能过。但它说明装了生产机用不到的东西：eslint 与
Playwright 只在开发和 CI 里跑（代码检查、冒烟测试），它们要 Node 20+。

**怎么办**：生产机按 [3.5](#35-构建前端两平台相同) 用

```bash
npm ci --omit=dev
npm run build
```

`--omit=dev` 跳过这两个包，警告一条都不会出现，装的东西也少一大截。构建真正要的
`vite` 与 `@vitejs/plugin-vue` 在 `dependencies` 里，不会被跳过。

**顺带一提**：**别用 `npm install`**。它在锁文件与 `package.json` 对不上时会顺手改锁文件，
于是每台机器装出各自的依赖版本；上面那条 `playwright-core@1.62.1` 就是这么来的——
仓库里钉的是 `1.56.1`，`npm install` 把它升到了最新的次版本。`npm ci` 严格按锁文件装。

### 7.10 Excel 里程碑导出成了表格而不是时间轴

Linux 缺中文字体，装一下：`sudo apt install -y fonts-noto-cjk`，然后重启后端。
字体在非常规目录时用 `APP_CJK_FONT` 指定。Windows 不会遇到这个问题。
