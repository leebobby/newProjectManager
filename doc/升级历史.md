## 怎么用这份文档

1. 先弄清楚你**现在跑的是哪个版本**：`cd <应用根目录> && git log --oneline -1`，
   再对照 [README 的更新记录](../README.md) 找到它对应的版本号。
2. 在下面的索引表里，从**你现在的版本**往上数到**要升到的版本**，
   中间跨过的每一条都要看——升级是累积的，跳过中间版本不代表跳过它的数据变更。
3. 每条只看「要额外做什么」那一列；写着**按标准步骤即可**的可以直接跳过正文。

> 条目里的命令按 **Linux** 写法给出（`sudo systemctl` / `/opt/aipm/...`）。
> Windows 上把重启后端换成 `Restart-Service aipm-backend`、Nginx 重载换成
> `C:\nginx\nginx.exe -s reload`、路径换成 `C:\aipm\...`，其余步骤一致，
> 对照 [部署指南 5. 差异速查](部署指南.md#5-linux-与-windows-差异速查) 即可。

## 补记（尚未编入版本号）→ 版本体系改三层 + 需求按项目度量与判重 + 问题单跟踪与超期统计 + 客户面/归组分类修边界

**本版是这几个版本里升级风险最高的一个**：`0010` 会**改动版本数据的组织方式并删除少量行**。
备份不是走过场，请务必确认 [4.1](部署指南.md#41-升级前必做) 的第 ① 步真的执行了。

**本条要动手的三件事**（其余按 [标准升级步骤](部署指南.md#42-标准升级步骤linux) 即可）：

| 做什么 | 在哪看 | 漏了会怎样 |
|--------|--------|-----------|
| 核对版本三层迁移（四步） | 下方「升级步骤」的 ①–④ | `0010` 会改动版本数据的组织方式并删少量行，是这几个版本里风险最高的一处 |
| 把 `config.json` 挪出版本库 | 紧接着这张表 | 问题单采集**悄悄停摆**：路径被换成模板里的空值，页面一切正常，只是再也采不到东西 |
| 手动重采一次问题单 | 紧接着这张表 | 领域管理与度量看板的「超期未处理」会一直显示「超期未知」 |

**可选：清理存量数据**（都**默认只读预演**，看清楚要改什么再加 `--apply`；改前先备份）

本版修了两处「分类把名字从中间切开」的老问题，采集侧从此不会再错，但**已经落盘的数据
不会自己重算**；同时给需求录入加了判重，**已经录重的也不会自己消失**。两个脚本都在
`backend/` 下跑：

```bash
cd <应用根目录>/backend
source venv/bin/activate                      # Windows: .\venv\Scripts\Activate.ps1

# 1) 历史快照的「客户面 / 所属小组」重算
#    修的是 "1号机" 认走 "11号机"、"张伟" 认走 "张伟明" 这两类
python scripts/repair_issue_dimensions.py               # 预演，打印「旧 → 新 : 条数」
python scripts/repair_issue_dimensions.py --apply

# 2) 迭代需求里已经录重的行
#    --apply 只删「六个进展全未开始、数字与备注全空」的空壳行，每组至少留一条；
#    被人填过内容的重复行不自动删，只列出来让人合并
python scripts/find_duplicate_requirements.py
python scripts/find_duplicate_requirements.py --apply
```

> 不跑这两个脚本也不影响使用：新数据从此是对的，只是历史那段仍按老规则分着类。
> 跑之前务必先看预演输出——重算会改动趋势图里的历史数字。

**把 `config.json` 挪出版本库（一次性）**

`backend/config.json` 从这个版本起不再入库（它是本机状态：绝对路径、要采集的项目，
而且页面「配置」会改写它）。你机器上的那份是被 git 跟踪且已被本地改过的，
直接 `git pull` 会因为"本地修改会被覆盖"而失败。做法是先备份、让 git 删掉它、再放回来
——放回之后它已经在 `.gitignore` 里，以后每次升级都不会再被碰：

```bash
cd <应用根目录>
cp backend/config.json ~/config.json.bak          # 先备份，这一步别省
git checkout -- backend/config.json               # 丢掉本地改动，让 pull 能顺利删除它
git pull origin main
cp ~/config.json.bak backend/config.json          # 放回来；此后它是未跟踪文件
python -c "import json;json.load(open('backend/config.json'));print('config OK')"
```

```powershell
cd <应用根目录>
Copy-Item backend\config.json $HOME\config.json.bak
git checkout -- backend/config.json
git pull origin main
Copy-Item $HOME\config.json.bak backend\config.json
```

> 漏掉这一步的表现是**问题单采集悄悄停摆**：`issue_api_script_path` /
> `issue_snapshot_dir` 被换成模板里的空值，页面一切正常，只是再也采不到东西。
> 备份脚本（[部署指南 6 章](部署指南.md#6-数据备份与恢复)）本来就在拷 `config.json`，
> 真丢了也能从最近一次备份里取回。

**重采一次问题单，「超期未处理」才有数**

这个数字是拿 DTS 的「预计闭环时间」（`planCloseTime`）跟今天比出来的，而这个字段
是这次才在 [scripts/fetch_issues_api.py](../backend/scripts/fetch_issues_api.py) 的
`FIELD_MAPPING` 里接上的。**已经落盘的历史快照里没有这一列**，所以升级后到下一次
采集之前，领域总览的问题单那一格会显示「超期未知」——这是如实的，不是坏了。
手动点一次「问题单管理 → 立即采集」即可立刻有数。

采完仍然全是「超期未知」的话，是 DTS 那边这个字段不叫 `planCloseTime`。
查法：采集一次后打开快照明细 JSON（`issue_snapshot_dir` 下的
`<项目>/<日期>.json`），看有没有 `estimated_close` 且有值；没有的话把
`FIELD_MAPPING` 里 `"planCloseTime"` 换成 DTS 实际返回的那个键名。

> 这个字段取不到**不影响其它任何功能**——采集、统计、趋势、差分都照常。
> 页面显示的是「超期未知」而不是「超期 0」：后者会被读成"一条都没超期"，
> 而实际是这个数算不出来。

**变更内容**

1. **版本体系两层改三层**（Alembic `0010`）：
   `major_versions` 大版本（`C10SPC100`，号段，自己不发布）→ **新表** `release_versions`
   版本（`C10SPC101/102`，真正对外发布的一级）→ `iteration_versions` 迭代版本
   （`C10SPC101B001`，构建）。
   - 老库的 `iteration_versions` 里**混着两级**（`C10SPC101` 和 `C10SPC101B001` 同层），
     迁移按 `B<数字>` 后缀劈开：带后缀的是构建，不带的提升为「版本」。
   - **被提升的原行只有在没被需求引用时才删**；仍被 `*_requirements.target_version_id`
     引用的**保留**，页面上会看到「版本」与同号「构建」并存，需要人工确认后清理
     （宁可留个重复项，也不能把别人填了半年的计划交付版本 SET NULL 掉）。
   - 各页面改看哪一层：客户面（现场版本、定制化需求的预计合入版本）→ **版本**；
     迭代管理与问题单 → **迭代版本**；版本达成率 → **版本**（接口入参由
     `major_version_id` 改为 `release_version_id`）。
2. **大版本主干 / 分支**：`major_versions` 加 `line` / `branch_name` / `branched_at`。
   主干只能通过「设为主干」按钮切换（同一事务里把原主干降为分支），页面上不会出现两个主干。
   迁移按版本号自然序把每个项目里最大的那个设为主干——**这是猜的，升级后必须人工确认**。
3. **版本三层自愈**（Alembic `0012`）+ 体检脚本，见下面的「必做步骤 ③」。
4. **客户面支撑看板**（Alembic `0011`）：`business_trips` 加 `project_id`（支撑项目）/
   `support_mode`（现场支撑·线上支撑）/ `man_days`（工作量人天）。
   **老数据的支撑方式全部回填成「现场支撑」**（改造前这张表登记的就是出差），
   项目与人天留空（人天留空时按起止日历天数推导）。
5. **问题跟踪页提速 + 默认只看未闭环**：日期列改成点开才挂控件、行内下拉不再预渲染选项、
   表格分页 50 条/页。「含已闭环」复选框**默认不勾**，导出跟随该开关。纯前端改动。
6. **版式模板并入专项配置**：顶层菜单「专项模板」下线，改为「专项管理 · 专项配置」页的
   第二个 Tab。`/special-templates` 保留为重定向，老书签不会 404。
7. **版本三层可手工排序、可改挂父级**：三层各有一个整体提交的 `reorder` 接口，
   页面上用「上移 / 下移」调整；版本 / 迭代版本的编辑框里可以改挂到别的父级
   （挂过去排在新父级末位，版本名下的构建跟着一起搬）。纯代码改动，无迁移。
   ⚠️ 三张版本表的**列排序（点表头排序）已取消**——它每次渲染都会盖掉手排的顺序。
8. **迭代需求加「项目」列 + 度量看板按项目度量**（Alembic `0013`）：
   `iteration_requirements` / `iteration_product_requirements` 各加一列 `project_id`。
   迭代本身是按年月排的、不属于任何项目，所以项目维度只能挂在需求行上。
   - **老数据一律留空**，不按「库里只有一个项目就全填它」猜——猜出来的归属在有了
     第二个项目之后就是看板上无人察觉的偏差。
   - 度量看板顶部新增「度量项目」下拉，作用于版本完成率 / 迭代质量 / 组级负载三个 Tab
     （调试版本看板按客户统计，不受影响）。**按项目筛时没填项目的行不计入任何项目**，
     页面会用一条黄条如实报出「还有 N 条需求没填项目，未计入本次统计」。
   - 两份 Excel 导入模板都多了一列「项目」，按项目名完全匹配；对不上留空不报错，
     导入后在页面上补选。
9. **「已变更」的需求整行不进统计**（无迁移，纯代码）：任一进展子项标了「已变更」的需求，
   在迭代管理里**整行置灰**（工具条另有「隐藏已变更」开关，默认不勾），
   并且**不再计入度量看板的任何口径，也不计入领域总览的需求统计**。
   ⚠️ **这是对旧口径的反转**：原来「已变更」按 0.5 加权算作"变更后仍在做"。
   升级后各看板的数字会立刻变化（总数变小、平均完成度通常变高），**这不是 bug**——
   页面上会用一条黄条如实写「有 N 条需求标了『已变更』，已整行排除」。
10. **迭代需求按项目分标签**（无迁移，纯前端）：领域需求 / 产品需求两张表上方各多一排
    项目标签（全部 / 各项目 / 未指定项目，带条数），原来的「按项目筛选」下拉去掉了。
    两个 Tab 共用同一个项目选择；停在某个项目标签上时，新增的需求默认归它。
11. **领域总览可按版本统计**（无迁移，纯代码）：页头多一排口径标签「按迭代 / 按版本」，
    具体哪个月、哪个版本由旁边的下拉选。选版本时统计的是该**版本**（C10SPC101 这一层）
    上的需求，**跨迭代**，此时月份选择不生效
    （两者叠加会得到一个既不是这个版本、也不是这个迭代的数）。
    版本下拉只列**当前挂着需求**的版本；一个版本都没挂需求时下拉是空的、旁边写着
    「还没有需求填了计划交付版本」，**这不是坏了**——需求的「计划交付版本」还没填
    或还没反查上 FK。
12. **客户面问题跟踪页可以直接新增**（无迁移，纯前端）：工具条多一个「新增」按钮，
    弹窗里先选客户再选机台（条目始终挂在机台上）。接口是原来就有的
    `POST /api/customer-issues`，**登录用户即可新增**，没有新的权限要配。
13. **度量看板按「版本 / 领域」两个质量维度重排**（无迁移，纯代码）：四个 Tab 收成三个
    ——版本质量（整个版本，跨迭代）/ 领域质量（一个迭代）/ 组级负载。
    新增接口 `GET /api/metrics/domain-quality/{iteration_id}`（登录用户可读，同其它度量接口）；
    `GET /api/metrics/version/{id}` 多返回 `by_domain` / `issues` / `issue_projects` 三块，
    老字段一个没删，**没有前后端版本耦合**。
    版本质量的「采集问题单」两列读的是**问题单管理的最新快照**（同领域总览那一份，
    数据源逻辑已收口到 `routers/_issue_source.py`）：还没接 API 采集的部署会回退到
    老的问题单 Excel，两者都没有时那两列留空并在表上方说明原因，**不影响其它列**。
    **「调试版本」看板挪到了「版本管理 → 现场调试版本」页顶部**（默认展开的折叠块）——
    用惯了的人会先去度量看板找，升级后知会一声。

14. **PPT 导出重排版**（无迁移，纯代码）：客户面状态 / 迭代需求 / 缺陷统计报表三处导出
    改成按内容自动分页，每页重复表头并带页码；列宽归一化铺满页宽；长文本列截断并标
    「另 N 条」；宽矩阵按列切页；问题单 URL 变成可点的「查看」。
    **接口与文件名都没变**，前端不用动；导出的页数会比以前多（以前是把所有行画在一页上、
    多出来的部分在幻灯片外面看不见）。依赖仍是 `python-pptx`，**没有新依赖**。

15. **领域管理补三个字段**（Alembic `0014`）：
    - 「事务与风险跟踪」加**责任人**（`domain_risks.owner_id`，人员下拉）和
      **风险等级**（`risk_level`，高/中/低）。原来只到「责任领域」这一层，而领域是个组，
      组不会去闭环一条风险。
      ⚠️ **风险等级不是优先级的别名**：优先级答"先处理哪个"、等级答"爆了有多疼"，
      一条低优先级的高等级风险（短期不动、但爆了很惨）是常态。所以**没有拿优先级回填**，
      老行的等级一律留空＝「还没评过」，和「评过是中」在页面上要能分开。
      风险等级**允许留空**——这张表里事务行和风险行混着，事务本来就没有等级。
    - 「遗留问题」加**当前进展**（`domain_legacy_issues.progress`），富文本，
      支持加粗 / 字号 / 颜色 / 多行，表格里限高 96px 内部滚动。
    - 「事务与风险跟踪」原有的**当前进展**（`domain_risks.progress`）也从纯文本
      **改成同款富文本**（列本身不变，无迁移）。这一列存了多年纯文本，所以出口过一道
      `_rich_to_html()`：看着像 HTML 的清洗，纯文本的转义并把换行转成 `<br>`，
      **老条目显示成什么样和升级前一模一样**，不用做任何数据处理。
    新增的三列老行都留空，**没有数据回填、没有口径变化**，升级后各页面数字不变。

16. **迭代版本加「实际发布日期」，发布过的版本不再进「计划交付版本」下拉**
    （Alembic `0015`）：`iteration_versions` 加一列 `actual_release_date`
    （「版本」那一层早就有这一列）。迭代管理里选计划交付版本时，
    **已发布的构建不再列出来**——否则可选项只增不减，一年下来几百个构建里绝大多数是历史。
    - 判定是「填了实际发布日期**并且那天已经过了**」，不是"填了就算"：
      发版计划一定就会先把日期填上，那之前版本还在收需求。
      构建所属的**版本**一旦发布，它名下的构建也一并收起来。
    - **老行一律留空**，不拿「预计发布日期」回填——计划跟实际不是一回事，
      拿计划当实际会把一批其实还没发的构建从下拉里抹掉，而使用者只会觉得
      "这个版本怎么选不到了"。所以**升级后下拉里一个都不会少**，
      要收哪个由人去版本管理页填日期。
    - **已经填在需求行上的版本不会因此显示不出来**：那一列存的是版本号字符串，
      下拉又允许自由输入，选项里没有也照常显示原值、也仍然可以手敲。
    - 客户详情页「客户定制化需求」的**预计合入版本**同样只列未发布的**版本**
      （C10SPC101 这一层）。这一列原来是个纯文本框，现在是可搜索的下拉，
      **仍然可以直接敲**——老数据里什么写法都有（"老口径 V3.2（待确认）"之类），
      强行只能选会逼着人把对不上的行改成一个错的版本。已填的值照常显示，不会变空。
    - 客户面状态的「现场版本」、度量看板的版本下拉、问题单管理**都不受影响**——
      客户装的多半就是已发布的版本，接口只是多带一个 `released` 标记，服务端没有过滤。
    - 顺带修了一个老问题：定制化需求那张表里，把「是否涉及其他项目」或「预计合入版本」
      **清空后保存，一刷新又回来了**（清除按钮把值置成 `undefined`，被 JSON 序列化丢掉，
      后端按"没传＝不修改"处理），而页面还提示保存成功。纯前端修复。

17. **问题单：责任人不在小组名单里的单不再被丢掉**（无迁移，纯代码）：
    采集时归不到小组的行以前是**直接丢弃**的，而「新增/解决」是相邻快照的编号差集
    ——**从不读问题单状态**，一单只要从快照里消失就记一笔「解决」。
    于是"问题单从定位转到实施修改、顺手转给了名单外的人"会表现成
    **还在处理中的单被算成已解决**，数字与图都自洽，看不出异常。
    - 现在这类行**保留在统计里**，小组归到「未归组」。丢的那条路彻底堵掉。
    - 归不到组的人会在两处提示：**采集完成时**弹一条黄色提示列出前几位；
      **配置 → 小组配置**底下新增「未归组责任人」表（责任人 / 部门 / 问题单数），
      每行可直接选一个小组「加入」，点了立刻落盘并刷新。
    - 这份清单从最新快照的明细文件**现算**，不入库——名单一改它就跟着变。
    - **部门过滤没有改**：部门答的是"这单归不归我们管"，答否就该出统计。
      升级后如果「解决」的数字比以前小了，那正是以前多算的部分。
    - 已经落盘的历史快照**不会被追溯修正**（快照就是当天的事实）。想让某天的差分
      重算，只能重新采集覆盖那一天；一般不必——补完名单后，从下一次采集起就正常了。

18. **采集脚本拉不全时整次失败，不再落短快照**（无迁移，改的是
    `backend/scripts/fetch_issues_api.py`）：翻页时任何一页返回
    `data: null`（DTS 会话中途失效的典型返回，**HTTP 状态是 200**）、
    中间页返回 0 条、或最后总条数少于接口自报的 `total`，都会让本次采集**失败**，
    不写快照。
    - 以前这些情况被 `or []` 吞成空页：**少拉一页（200 条）的快照看起来完全合法**，
      第二天的差分就给出 200 条假「解决」。
    - 代价是**采集失败会变多**（以前是"悄悄少一半"，现在是"明着失败"）。
      失败原因写在「采集日志」里，多数是 Cookie 过期，按
      [7.7](部署指南.md#77-问题单采集失败) 换掉重跑即可。
    - 拉回来的**多于** `total` 不算失败（翻页期间有单增删导致行位移，多出来的是重复行，
      去重会处理），只在脚本 stderr 上留一行提示。
    - **如果你没有在服务器上覆盖过这个脚本**（用的是仓库里的那份），跟着代码一起更新即可；
      如果曾经手工改过（例如换过 `PROJECT_PARAMS` 或凭据），**记得把这次的改动合进去**，
      否则假解决还会继续。

19. **专项管理新增「总览」页**（Alembic `0016`）：一张跨专项的横表，
    七列——序号 / 关键专题 / 目标 / 风险（红黄绿点灯）/ 关键进展 / 关键风险和措施 / 责任人。
    在侧栏「专项管理」下，**所有登录用户可见**（它只读各专项已有的字段）。
    - **六列全部自动提取，没有任何一处要另填一遍**：目标＝专项目标分段，
      关键进展＝整体进展分段，关键风险和措施＝风险和问题分段里**还没闭环**的行
      （风险与措施分开显示，超期的排前面），责任人＝专项责任人。
      在对应专项的详情页里改，总览刷新就跟着变。
    - **点灯按风险行自动判**：一条风险都没登记＝**未评估**（灰），不是绿——
      记成绿的话，最该被追着去补风险的那几个专项在总览上看着比谁都干净；
      登记过且全部闭环＝绿；有未闭环的＝黄；有未闭环且**已过**计划闭环时间＝红。
      当天到期不算超期；没填计划闭环时间的未闭环行只顶到黄（那是"没排期"，
      不是"排了没做到"）。
    - 灯可以**人工指定**（点那一格），指定之后就不再跟着风险行走了，
      页面上带一个 ✎ 标记，弹窗里同时显示"自动判定是什么"。用完改回「自动判」即可。
      写权限＝登录用户，与详情页共用同一个乐观锁。
    - `special_contents` 加一列 `overview_light`（存人工指定的值，空＝自动）。
      **老行一律留空**，不按当前风险行回填：回填等于把"当时算出来的灯"凝固成"人拍的板"，
      此后风险闭环了灯也不会变，而页面上看不出这个灯是死的。
    - 可**导出 PPT**（页面右上角），与页面同口径：导出直接用总览接口的返回值，
      不另查一遍库、也不另算一遍灯。副标题里报灯的分布，以及「其中 N 项的灯为
      人工指定」——不报的话，这份材料等于把人拍的板摆成了系统算出来的结论。
      风险一格塞不下时写明「另 N 条，见系统」。
    - 顺带把点灯的配色收进 [brand.py](../backend/brand.py)（`LIGHT_FILLS` /
      `LIGHT_TEXTS`）。原来这套颜色只写在 Excel 那一侧，PPT 要用就得抄一份，
      而抄完就会慢慢分叉成「同一盏灯在两份文件里颜色不一样」。**纯重构，
      导出的颜色一个都没变。**
    - **升级后不用做任何事**，也没有数据变化——所有专项第一次打开总览就有数字。

20. **专项 Excel 导出改版**（无迁移，改的是 `backend/xlsx_utils.py`）：
    - **一个专项导出成一张表**。以前自定义的自由表格因为列宽对不上被丢到独立工作表、
      正文里只留一行「→ 见工作表「X」」，一份周报打开是四五个页签，
      章节顺序和上下文全断在那行指引上。现在所有分段（含自由表格）按页面顺序
      在同一张表上往下排，页签只有一个。
    - **里程碑时间轴修了三处**：日期统一成 `YYYY-MM-DD`（库里这一列是自由字符串，
      `2026-05-20T00:00:00`、`2026/7/1`、毫秒时间戳都存在，以前原样画上去，
      一个串到隔壁节点、一个和别人对不齐）；**英文不再从单词中间断开**
      （以前 "Release" 会断成「Releas / e」）；里程碑多了**换行摆**而不是把图
      一路加宽（以前十几个里程碑的图会横着甩出表格外面老远）。
      认不出来的日期（「6月中旬」这类）**原样保留**，不丢。
      周报（HTML / 纯文本）与 Excel 现在共用同一份日期归一。
    - **边框补全**：合并区在 xlsx 文件里只留左上角那一格，而 Excel 画合并区的框是
      按边上每一格取的——以前只给左上角设了框，打开看就是每段后面一条 A 列那么宽的
      小短线，右边整个没有框。现在整幅合并的行逐格写，并且**按「分段」压外框**
      （章节标题行 + 内容在一个框里），整页从"一堆浮着的横条"变成一段一个块。
    - **图片后面不再空半屏白**：预留行数按每行 20px 算（以前按 18px 还多加 2 行）。
    - 打印默认横向、按宽度缩到一页宽——不设的话默认纵向 A4，一份宽表打出来
      被从中间劈成左右两叠。
    - **升级后不用做任何事**，重新导出一次即可；已经导出过的旧文件不受影响。

**① 确认迁移追平到 `0016`**（不是可选项，见 [4.4](部署指南.md#44-数据库结构是怎么追平的)）：

```bash

source venv/bin/activate                 # Windows: .\venv\Scripts\Activate.ps1

```

**② 看一眼 `0010` 的迁移汇总**。它会在后端启动日志里打印一行：

```
[0010] 版本三层迁移完成：生成版本 N 个，删除被提升的冗余迭代行 M 条，因仍被需求引用而保留 K 条
```

```bash
sudo journalctl -u aipm-backend -n 200 --no-pager | grep '\[0010\]'    # Linux
```
```powershell
Select-String -Path C:\aipm\logs\backend*.log -Pattern '\[0010\]' | Select-Object -Last 5
```

**K 就是需要你去页面上人工归位的行数**——那几条会同时以「版本」和同号「构建」出现。
打开版本管理页找到它们，确认后删掉多余的那个构建即可。K=0 就没这回事。

> 迁移只在**第一次**追平时打印这一行，日志滚掉了就抓不到了。没找到不要紧——
> 步骤 ③ 的体检脚本会把同样的信息重新算一遍。

**③ 跑一次版本三层体检**（**只读，不改库**）：

```bash
cd <应用根目录>/backend
source venv/bin/activate                 # Windows: .\venv\Scripts\Activate.ps1
python scripts/repair_version_tiers.py
```

> 一定要**先激活 venv 再跑**：直接用系统 `python` 会因为缺 SQLAlchemy 报
> `ModuleNotFoundError`，而不是脚本本身有问题。

关注输出里的「迭代版本 N，其中**没挂上版本**的 M 条」：

- **M = 0** → 正常，跳过下面这段。
- **M > 0** → 上一次迁移跑了一半（SQLite 下 Alembic 是 non-transactional DDL，
  中途失败时加过的列会留在库里；`0010` 的回填守卫看到 `release_versions` 非空就整段跳过，
  于是剩下的迭代行永远挂不上版本）。这些行在页面上**完全不可见**，
  现象就是「迁移完版本信息全丢了，只剩第一层」——但**数据一条都没少**。
  修法二选一：
  - 重启一次后端，`0012` 会自动把它们挂回去（只挂接、不删任何东西，可反复执行）；
  - 或者用脚本，多一步「清掉本身就是版本、且无人引用的冗余行」：

    ```bash
    cp app.db app.db.bak                                   # 先备份（Windows: copy app.db app.db.bak）
    python scripts/repair_version_tiers.py                 # 看修复预演
    python scripts/repair_version_tiers.py --apply         # 确认后执行
    ```

**④ 确认主干归属**。迁移按版本号自然序猜了主干（每个项目里号最大的那个），
实际哪个大版本跑在主干上只有你清楚。打开版本管理页看「代码线」列，不对就点「设为主干」——
该按钮会在同一事务里把原来的主干降为分支，不会出现两个主干。

  ```sql
  -- 例如保留最近 6 个月
  DELETE FROM operation_logs WHERE created_at < datetime('now','-6 months');
  VACUUM;
  ```
- 闲置阈值若需调整，修改 [frontend/src/App.vue](../frontend/src/App.vue) 中的常量 `IDLE_MS`。

## v0.10.x → 客户面状态清单字段格式变更

**变更内容**

`customer_status` 表的两个文本字段存储格式由纯文本改为 JSON 数组：

| 字段 | 旧格式（纯文本） | 新格式（JSON） |
|------|-----------------|----------------|
| `recent_focus` | `"良率提升\n备件采购"` | `[{"text":"良率提升","done":false},{"text":"备件采购","done":false}]` |
| `key_issues` | `"主控板偶发复位"` | `[{"text":"主控板偶发复位","done":false}]` |

**是否需要修改数据库？不需要。**

两个字段仍然是 `TEXT` 类型，表结构无任何变化。旧数据可直接使用，无需运行任何迁移脚本。

**兼容原理**

前端在读取字段时会自动判断格式：

```
读取字段值
    ├── 能解析为 JSON 数组 → 直接作为清单条目渲染（新格式）
    └── 否则按换行符拆分  → 每行作为一个未勾选条目渲染（旧格式自动兼容）
```

旧数据在用户第一次对该行执行操作（勾选、新增条目、点「保存」）后，才会被写成新 JSON 格式，之前一直保持原样。

**PPT 导出兼容**

`pptx_utils.py` 已同步更新，导出时自动将 JSON 清单转为可读文本：

```
✓ 已完成的条目
· 未完成的条目
```

旧纯文本字段原样输出，不受影响。
